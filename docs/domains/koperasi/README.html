Koperasi

Domain manajemen koperasi terintegrasi di SekolahPro, mencakup operasional simpanan-pinjaman (konvensional & syariah), layanan sosial (ZIS & wakaf), pengelolaan kas teller, persetujuan, dan pelaporan. Mendukung two modes operasi: Konvensional (bunga) dan Syariah/BMT (akad syariah + baitul maal).

Arsitektur

  • Backend: Frappe app sekolahpro, module koperasi (repo terpisah, tidak dalam web repo ini)
  • Frontend (web): Package @sekolahpro/app-school, shell /kop/$sekolah (TanStack Router, React 18)
  • Routes prefix: /kop/$sekolah/* (mis. /kop/sd-maju/transaksi)
  • Shared packages: @sekolahpro/api-client (Frappe resource hooks), @sekolahpro/ui (primitives + layout)
  • Mode runtime: Hook useKoperasiMode() membaca singleton Frappe Pengaturan Koperasi (field mode_koperasi: "Konvensional" vs "Syariah (BMT)")

Alur Utama

  1. Onboarding Anggota: Calon anggota → form pendaftaran → dokumen upload → verifikasi → created Anggota Koperasi (status: Pending) → approval → Aktif
  2. Pembukaan Rekening: Anggota aktif → pilih produk simpanan → create Rekening Simpanan (Pokok/Wajib/Sukarela) → link dengan anggota
  3. Transaksi Simpanan: Teller via kasir / RFID → pilih jenis (Setor/Tarik/Transfer) → validate saldo & nominal → create Transaksi Simpanan → update rekening saldo
  4. Pembiayaan (Akad): Anggota apply → pilih produk & tenor → sistem generate Jadwal Angsuran → create Akad Pembiayaan (status: Draft) → approval by supervisor → Berjalan (dilepas dana) → cicilan masuk via transaksi atau bayar langsung
  5. Sesi Kas Teller: Teller buka shift → input modal kas & denominasi → sistem track transaksi → end-of-shift tutup sesi → validate denominasi fisik vs sistem → selisih dicatat & approval
  6. Persetujuan: Supervisor inbox menampilkan permohonan (Buka/Tutup/Blokir/Unblokir/Aktivasi Dormant) → review nasabah/rekening → approve (Disetujui) atau reject (Ditolak, mandatory alasan_penolakan)
  7. ZIS / Wakaf (syariah only): Catat penerimaan ZIS (jenis: Zakat/Infak/Sedekah/Wakaf Tunai) → atau catat aset wakaf (properti, tanah, dll) dengan jenis & wakif → track status produktivitas
  8. Pembagian SHU: RAT meeting → input total SHU & tanggal RAT → sistem generate baris per anggota (partisipasi) → status Disahkan → distribusi ke rekening anggota → Dibagikan

Aturan & Kebijakan

  • Mode adaptif: Menu sidebar & halaman menyesuaikan berdasarkan jenis koperasi (Konvensional vs Syariah). BMT melihat menu "Baitul Maal" (ZIS + Wakaf) dan label "Akad"; Konvensional melihat "Suku Bunga" read-only dan label "Pinjaman". Hook useKoperasiMode() membaca Pengaturan Koperasi.mode_koperasi dengan fallback syariah (superset) saat loading/error.
  • Sesi Kas guard: Transaksi simpanan hanya diizinkan jika ada Sesi Kas Teller aktif (status = "Aktif") untuk teller ybs. Helper hasActiveSession(sessions, tellerEmail) memvalidasi.
  • Transaksi validation: Setor/Tarik/Transfer nominal harus > 0, rekening harus valid. Transfer tidak boleh ke rekening yang sama. Tarik tidak boleh melebihi saldo (jika diketahui). Rule validateTransaksi() pure function.
  • Sesi Kas balance: Buka: sum(denominasi_buka) == modal_kas (mandatory). Tutup: selisih = sum(denominasi_tutup) - saldo_seharusnya; jika selisih != 0 maka catatan_selisih mandatory.
  • Akad Pembiayaan locks: Field akad_type (Murabaha/Musharaka/Qard/dll) read-only setelah submission (role-based). Jika mode konvensional, hanya bunga (interest), tidak ada akad syariah.
  • Permohonan approval: Setiap permohonan (Buka/Tutup/Blokir/dll) lifecycle: Draft → Diajukan → (Disetujui | Ditolak). Ditolak wajib isi alasan_penolakan. Trigger backend hooks untuk update status rekening/anggota.
  • ZIS / Wakaf (syariah only): Penerimaan ZIS status dapat "Diterima" (verified) atau "Pending". Aset Wakaf status "Produktif" (menghasilkan) vs "Tidak Produktif" (disimpan). Halaman ZIS & Wakaf hidden untuk mode Konvensional.
  • SHU read-only render: Halaman laporan SHU menampilkan total simpanan, pembiayaan berjalan, macet, & anggota aktif via aggregates dari list queries. Detail laporan syariah (PSAK 101-110), mutasi kas, rekonsiliasi deferred (Phase 3).
  • E-money / Kartu RFID: Transaksi kartu via merchant → log Transaksi Kartu → update rekening saldo. Card activation via anggota profil. Lost/damaged card request new via supervisor.
  • Suku Bunga (konvensional only): Halaman read-only daftar Produk Pembiayaan dengan margin_pa, skema_angsuran, maksimal_tenor. Tidak ada form edit di frontend (editing via Frappe desk backend).

Cross-Domain Events

Triggers (memicu)

  • Anggota Koperasi status change Aktif → firevent untuk init default Rekening Simpanan (pokok wajib) jika belum exist
  • Akad Pembiayaan status change Draft → Berjalan → backend trigger pencairan dana (debit account pembiayaan, kredit rekening simpanan anggota)
  • Jadwal Angsuran due date past & unpaid → backend trigger overdue notification / status change Terlambat
  • Sesi Kas Teller status change Aktif → Pending Approval → supervisor notification (inbox persetujuan)
  • Pembagian SHU status change → Disahkan → Dibagikan → backend trigger distribusi ke rekening (batch journal entries)

Listens (bereaksi)

  • Periode Tutup Koperasi status closed → freeze transaksi baru (guard: transaksi periode lalu ditolak), allow reversal hanya untuk adjustment
  • Pengaturan Koperasi.mode_koperasi change → frontend re-render sidebar filterKoperasiNav(), halaman ZIS/Wakaf toggle visibility
  • E-money / Merchant activation → Transaksi Kartu acceptance (validation merchant aktif sebelum posting)

Batas Ruang Lingkup (YAGNI)

  • Suku Bunga editing: Frontend read-only hanya; editing via Frappe desk. Tidak ada form CRUD client-side.
  • Laporan detail syariah: PSAK 101-110 (neraca syariah), detail SHU per kategori (mudharabah/musharaka/dll), mutasi kas teller per shift, rekonsiliasi → Phase 3 (out-of-scope sprint ini).
  • Anggota approval workflow: Draft → Aktif onboarding via wizard simpel, bukan full approval inbox (approval inbox hanya untuk permohonan transaksi: Buka/Tutup/Blokir rekening).
  • Batch operasi: Bulk close rekening, bulk freeze anggota → deferred; frontend list hanya render, no multi-select action.
  • SHU calculation engine: Backend pure; frontend hanya tampilkan hasil. Tidak ada client-side calculation / simulasi SHU (complex formula, must be server).
  • Sanctions match / AML: Manual add ke Sanctions List Entry master; system alerts anggota baru nama match (Phase 3 auto-sync dengan DTTOT API).
