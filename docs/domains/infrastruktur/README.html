Infrastruktur / Sarpras

Mengelola struktur fisik sekolah: gedung, lantai, ruangan (dengan fasilitas terlampir), dan utilitas publik (listrik, air, internet, gas). Mendukung CRUD lengkap dengan konteks hierarki dan tenancy per sekolah.

Arsitektur

  • Backend module: sekolahpro (repo terpisah) — mendefinisikan doctype Gedung, Lantai, Ruangan, Fasilitas Ruangan (child, istable=1), Utilitas Gedung, dengan kontrol tenancy dan autoname
  • Frontend route prefix: /sch/{sekolah}/infrastruktur — landing page (infrastruktur.index), daftar gedung (daftar-gedung), detail gedung CRUD inline (daftar-gedung.{gedungId}), plus route modul terpisah per entitas (lantai, ruangan, utilitas)
  • Shared packages: @sekolahpro/ui (komponen Modal, DataTable, Button, FormField, Badge, SectionCard), @sekolahpro/api-client (useResourceCreate, useResourceUpdate, useResourceDoc, useResourceList, useResourceDelete), TanStack Router, TanStack Query (React Query)
  • File location: FE code di apps/school/src (routes, komponenmodal, lib helper). Backend doctype + hook di repo sekolahpro (tidak di repo ini)

Doctypes / Entitas

Doctype Peran Field Kunci
Gedung Entitas induk infrastruktur sekolah; akar hierarki nama (Data, reqd), kode (Data), tahun_dibangun (Int), sekolah (Link, tenancy scope)
Lantai Struktur vertikal di dalam gedung; induk Ruangan nama (Data, reqd), nomor_lantai (Int, reqd), gedung (Link, reqd), sekolah (denorm, readonly)

Fasilitas Ruangan Child table (istable=1) pada Ruangan — item peralatan/furnitur; scoped via parent parent (parent doc name), parenttype (Ruangan), nama_fasilitas (Data, reqd), jumlah (Int, default 1), kondisi (Select: Baik/Rusak, default Baik)

Alur Utama

  1. Landing Page Infrastruktur: User masuk /infrastruktur → dashboard dengan flow 4 tahap (Daftar Gedung → Lantai → Ruangan → Utilitas), aksi cepat, alert fasilitas rusak, dan tombol Tambah Gedung
  2. Daftar Gedung: List semua gedung per sekolah, search/filter, aksi buka detail atau buat baru via modal
  3. Detail Gedung + CRUD Inline: Tampilkan info gedung, 3 tab (Lantai / Ruangan & Fasilitas / Utilitas); tiap tab memuat list ter-filter per gedung; tombol Tambah membuka modal create; baris tabel punya aksi Edit (buka modal dengan edit mode) dan Hapus (konfirmasi, lalu delete); setelah mutasi, refresh tabel
  4. Modal Hierarchical Awareness: Modal Lantai menerima defaultGedung → terkunci ke gedung itu, tidak perlu pilih; Modal Ruangan menerima defaultGedung → filter Lantai dropdown per gedung, sembunyikan select Gedung/Sekolah (denorm BE); Modal Utilitas idem. Backward-compatible: caller lama tanpa prop = create lama
  5. Child Table Edit (Fasilitas via Ruangan): Ruangan memiliki grid fasilitas inline di modal — user klik Edit Ruangan → lihat grid + tombol Tambah/Hapus baris. Saat submit, kirim array fasilitas lengkap (full replace, Frappe REST spec)
  6. Query Invalidation: Setelah create/update/delete, query client panggil invalidateQueries({ queryKey: ["resource:list", "Lantai"] }) dll, TanStack Query auto-refetch

Aturan & Kebijakan

  • Tenancy: Semua entitas terscope ke sekolah aktif session (filter FE, verifikasi BE). Child table Fasilitas tidak punya field sekolah sendiri — scoped via induk Ruangan
  • Autoname backend: Lantai = {gedung}-L{nomor_lantai} (BE side), Ruangan = {lantai}-{kode}, Utilitas Gedung = {gedung}-{jenis}. Duplikat → DuplicateEntryError BE, ditampilkan di banner modal
  • Denormalisasi: Ruangan.gedung dan Ruangan.sekolah auto-set dari Lantai (hook BE), FE tidak kirim saat create/update. Utilitas Gedung.sekolah auto-set dari Gedung (hook BE)
  • Default status: Ruangan.status = "Tersedia" (default), Fasilitas Ruangan.kondisi = "Baik", Utilitas Gedung.status = "Aktif"
  • Delete constraints: Lantai tidak bisa dihapus jika ada Ruangan anak (LinkExistsError BE) — UI tangkap & tampilkan pesan error; Ruangan tidak bisa dihapus jika ada Fasilitas (child delete cascade BE, atau error jika diasingkan)
  • Permission: Saat ini hanya role System Manager di backend yang punya akses. Non-System-Manager REST call → 403. Keputusan deferred: buka untuk role sekolah (Sekolah Admin, Tata Usaha) via task follow-up BE (di repo sekolahpro)
  • Modal edit mode: Prop editName trigger useResourceDoc fetch, effect populate form, submit kirim patch dengan field yang berubah (tidak full doc). Backward-compat: caller tanpa editName = create only mode lama

Cross-Domain Events

Triggers (memicu domain lain)

Tidak ada. Domain infrastruktur tidak mengambil atau menginisiasi aksi di domain akademik (Kurikulum, Mapel, KKM, Tahun Ajaran), keuangan, atau administrasi. Struktur fisik berdiri independen.

Listens (bereaksi)

Tidak ada. Perubahan di domain lain (akademik, keuangan) tidak trigger reaksi infrastruktur. Jika master data akademik perlu tahu ruangan/kapasitas, itu diquery saat aplikasi akademik butuh (bukan event-driven).

Alasan: Infrastruktur adalah domain master-data (metadata sekolah). Sumber kebenaran untuk struktur fisik. Domain fungsional (akademik: penjadwalan, manajemen kelas; keuangan: invoicing ruang) query dan cache infrastruktur data saat dibutuhkan, tapi tidak mengirim event balik. Decopling sengaja untuk menghindari cascading updates dan memudahkan evolusi schema terpisah.

Batas Ruang Lingkup (YAGNI)

  • Child Riwayat pada Utilitas: Spec desain menyebut Riwayat Utilitas (child table, istable=1) di Utilitas Gedung untuk catat nilai meteran historis. Implementasi saat ini belum buat UI modal edit Utilitas dgn grid Riwayat inline — deferred ke task follow-up. Data model backend sudah siap; FE cukup extend modal UtilitasGedungFormModal dgn grid row editor jika diperlukan
  • Bulk import Gedung/Lantai/Ruangan: Dashboard saat ini support create one-by-one. Jika sekolah butuh setup 100+ ruangan, buat import CSV task terpisah (migrasi data, bukan CRUD inline)
  • Fasilitas Ruangan inventory tracking: Saat ini hanya catat nama, jumlah, kondisi. Tidak ada: nomor seri, tanggal pembelian, nilai aset, depreciation. Jika dibutuhkan, perluas schema + modal terpisah
  • Perencanaan Kapasitas (akademik-infrastruktur integration): Sistem akademik (penjadwalan) bisa query kapasitas ruangan dari infrastruktur. Tapi tidak ada fitur "cek konflik ruangan" atau "alokasi otomatis berdasarkan kapasitas" di infrastruktur sendiri — itu responsibility akademik module
  • Role-based permission UI: Saat ini asumsikan System Manager. Untuk non-admin access, follow-up task backend (repo sekolahpro) set permission di doctype, lalu FE auto-grant modal access (no UI change needed)
