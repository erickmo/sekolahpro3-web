PPDB (Penerimaan Peserta Didik Baru)

Modul penerimaan peserta didik baru dengan alur role-adaptive (staff/manajer), antrian kerja real-time, visualisasi funnel/quota/pembayaran, dan integrasi pembayaran. Didesain untuk operasional harian dan oversight manajemen dengan dashboard KPI, analytics murni, dan work-queue derivation.

Arsitektur

  • Backend Frappe module: sekolahpro.ppdb (repo terpisah); API whitelisted di sekolahpro.ppdb.api.ppdb
  • Web route prefix: /sch/$sekolah/ppdb dengan 9 halaman tab-based
  • Shared packages: @sekolahpro/api-client (useResourceList, frappeFetch), @sekolahpro/auth (useSession), @sekolahpro/ui (komponen, chart primitives)
  • Foundation libraries: ppdbRole.ts (derivasi peran staff/manajer), ppdbAnalytics.ts (agregasi murni), ppdbPaymentAnalytics.ts (metrik pembayaran), ppdbQueue.ts (antrean kerja 4-grup)
  • Mock fallback: data/ppdb.ts fixture calon peserta; wired via listPpdbForSekolah(sekolah) untuk preview sebelum backend siap. Mock menggunakan status internal (Terkirim, Verifikasi, Tes, Lulus, Tidak Lulus, Daftar Ulang) yang ditranslasi ke backend pipeline saat commit
  • State management: TanStack Query untuk resource list/doc + mutations dengan auto-invalidation per doctype

Doctypes / Entitas

Doctype Peran dalam alur Field kunci
Gelombang PPDB (inferred) Batch pendaftaran terikat tahun ajaran, jenjang, kuota, tanggal buka-tutup name, nama, tahun_ajaran, tingkat, kuota, tanggal_buka, tanggal_tutup, biaya_pendaftaran, status
Pendaftaran PPDB (inferred) Record calon siswa per batch; hub biodata, dokumen, pembayaran, hasil seleksi name, calon_siswa, gelombang_ppdb, status (Draft→Diajukan→Diverifikasi→Seleksi→Diterima/Ditolak→Selesai), tanggal_daftar, jalur, asalSekolah
Seleksi PPDB (inferred) Hasil tes/wawancara, ranking, keputusan lulus/tidak lulus per calon name, pendaftaran_ppdb, skor_tes, skor_wawancara, hasil (Lulus/Tidak Lulus), ranking
Pembayaran PPDB (inferred) Tagihan + pencatatan pembayaran (biaya pendaftaran, uang pangkal, SPP, seragam, buku) name, pendaftaran_ppdb, status (Lunas/Cicilan/Tertunda), jumlah, tanggal, metode (Transfer/QRIS/Tunai/Virtual Account)
Daftar Ulang PPDB (inferred) Konfirmasi calon diterima, data siswa baru, pemisahan alur lulus vs ditolak name, pendaftaran_ppdb, status (Selesai/Tertunda), siswa_baru (link ke Siswa setelah finalisasi)

Alur utama

  1. Buat Gelombang: Manajer setup Gelombang PPDB (tanggal, kuota, biaya) → halaman Pengaturan
  2. Pendaftaran: Calon siswa ajukan aplikasi via formulir public/staff entry → ciptakan Pendaftaran PPDB (status: Draft→Diajukan). Biaya pendaftaran auto-generate Pembayaran PPDB baris pertama
  3. Verifikasi Dokumen: Staff periksa berkas (KK, Akta, Rapor, dll) di halaman Calon Siswa; set status per dokumen (Belum→Diterima/Ditolak). Antrean dokumen di work-queue
  4. Pembayaran: Calon bayar biaya pendaftaran + uang pangkal + SPP via payment gateway (QRIS/Virtual Account) → Pembayaran PPDB status Lunas/Cicilan/Tertunda. Halaman Pembayaran track aging tagihan
  5. Seleksi: Panitia input skor tes akademik/wawancara di halaman Seleksi → ciptakan/update Seleksi PPDB. Ranking otomatis per jalur (zonasi, prestasi, dll). Tetapkan hasil lulus/tidak lulus via aksi di tabel yang sama
  6. Pengumuman: Manajer tekan tombol Umumkan Hasil pada halaman Seleksi → broadcast ke calon siswa. Pendaftaran PPDB status maju dari Seleksi → Diterima/Ditolak
  7. Daftar Ulang: Calon diterima konfirmasi kehadiran + submit data final (nama, alamat, dll) di halaman Daftar Ulang. Set status Selesai → trigger finalisasi
  8. Finalisasi: System convert Pendaftaran PPDB Selesai → ciptakan doctype Siswa baru (masuk akademik domain), link di Daftar Ulang PPDB. Selesai

Aturan & Kebijakan

  • Status pendaftaran pipeline (backend): Draft → Diajukan → Diverifikasi → Seleksi → Diterima/Ditolak → Selesai (atau Mengundurkan Diri). Hanya maju; tidak boleh mundur
  • Status internal frontend (mock): Draft, Terkirim, Verifikasi, Tes, Lulus, Tidak Lulus, Daftar Ulang, Diterima, Mengundurkan Diri — digunakan di fixture mock data sebelum backend siap
  • Jalur pendaftaran: Reguler, Prestasi Akademik, Prestasi Non-Akademik, Afirmasi, Zonasi, Mutasi Orang Tua — pisah kuota, ranking, kriteria
  • Verifikasi dokumen wajib: KK, Akta, KTP Ortu, Foto, Rapor, Ijazah, SKHU (jika ada), Surat Sehat, Sertifikat Prestasi (jika ada). Calon tidak boleh lanjut sampai semua "Diterima" (atau dipetakan ke "Ditolak")
  • Pembayaran tanggungan: Cicilan diperbolehkan hingga batas tanggal tertentu; setelah itu status jadi Tertunda (flagged untuk follow-up aging di staff queue). Payment aging report ≥14 hari
  • Ranking zonasi: Auto-rank berdasarkan jarak sekolah (jika tersedia) + nilai rata-rata rapor. Scoring logic per gelombang (configurable)
  • Kuota hard limit: Manajer set kuota per batch, per jalur. Sistem tidak bisa terima lebih dari kuota (reject otomatis atau queue untuk reserve)
  • Role-adaptive framing: Staff PPDB (operator, bendahara, admin_sekolah) → default view Antrian Kerja (apa yg harus dikerjakan). Manajer PPDB (kepala_sekolah) → default view Ringkasan (KPI + funnel + trend). Toggle di halaman Beranda membolehkan switch view tanpa batas. Access control tetap di backend
  • Permissive fallback: Jika session unavailable atau user punya peran tidak cocok, grant semua PPDB role agar UI tidak gated
  • Work queue (4 grup): Dokumen (belum/ditolak) → Seleksi (skor tes undefined) → Pembayaran (Tertunda) → Daftar Ulang (lulus/diterima belum selesai). Previewed di Beranda Antrian + deeplinks ke page terkait. Pure derivation dari list Pendaftar
  • Tahun Ajaran filter: Setiap Gelombang terikat tahun_ajaran master (akademik domain). UI auto-filter pendaftar per tahun aktif

Cross-Domain Events

Triggers (memicu domain lain)

  • Finalisasi Pendaftaran (→ akademik): Saat Pendaftaran PPDB status Selesai, system membuat doctype Siswa baru di domain akademik, auto-populate biodata (nama, nik, tempat lahir, dll). Parent link set ke Daftar Ulang PPDB
  • Tahun Ajaran reference: PPDB membaca Tahun Ajaran master dari akademik (filter batch, default tahun aktif)

Listens (bereaksi pada event domain lain)

  • Tahun Ajaran.on_change → PPDB auto-refresh dropdown gelombang aktif (UI-side TanStack Query invalidation)
  • Kurikulum, Mapel, KKM → read-only reference untuk tampil di preview calon (tidak mutate)

Batas ruang lingkup (YAGNI)

  • Kanban board: Desain awal (2025) punya kanban card view; redesain 2026 hapus (simplify ke table + queue)
  • Ujian online terintegrasi: Scope PPDB tidak cover test engine; skor tes diinput manual atau dari third-party LMS
  • SMS/Email bulk campaign: Notifikasi hasil (pengumuman, reminder pembayaran) dihandle di job queue terpisah, bukan di PPDB module
  • Advanced ML ranking: Zonasi ranking pakai logika sederhana (jarak + GPA); model ML future phase
  • Integrasi NISN real-time: NISN lookup dari data central saat registrasi (optional; user entry juga boleh)
  • Live payment reconciliation: Payment aging di UI pakai pull manual (reconcile button), bukan webhook otomatis (future: add webhook listener)
